    Lost vs preserved
    
      
    
      
    What happens to data in a real kernel panic
        
      
          
    • Lost — everything only in RAM: processes and their memory, run and I/O queues, network connections, open transactions, and the page cache — including dirty pages (writes the kernel had accepted but not yet written to disk).
      • 
          
    • Preserved — what was already on disk: files, and every database transaction that was committed with fsync. The file system's journal is replayed at boot, so its metadata is consistent again (ext4 default: metadata journalling).
      • 
          
    • kdump: if enabled, a second, small "capture" kernel boots and saves the crashed kernel's memory to disk as a vmcore file for later analysis (crash / gdb).
      • 
          
    • In this app the panic is simulated: the experiment history in SQLite (database/experiments.db) is never at risk, and each kernel experiment is saved there with its timeline and this lost / preserved list.

    Limitations of this simulation
      
      
        
    • Stage durations are illustrative simulated seconds, not measurements of real hardware.
      • 
        
    • Console lines are written to look like Linux output; they are not captured from a kernel.
      • 
        
    • The model does not emulate kernel internals (interrupts, page tables, drivers); it models what an operator sees: the panic, what stops, the boot sequence, what is lost and what survives.
      • 
        
    • A real panic can be studied safely only in a disposable virtual machine — see docs/KERNEL_LAB.md. The normal application never does this.
